## Registry entry changes (exact strings for registry.json; the registry owner applies them)

- prompt-input › docs: "Ported from Radix to Base UI. API changes vs AI Elements: (1) PromptInputActionAddScreenshot takes `onClick` instead of Radix `onSelect`; calling `event.preventDefault()` in it skips the capture, but the menu still closes (pass `closeOnClick={false}` to keep it open). Capture failures other than a denied or cancelled picker go to PromptInput's `onError` as `{ code: \"screenshot\", message }`, or to `console.error` when there is no handler. (2) PromptInputActionAddAttachments and PromptInputActionMenuItem are Base UI Menu items: use `onClick` (not `onSelect`) and `closeOnClick={false}` to keep the menu open. PromptInputActionAddAttachments calls your `onClick` first, skips the file dialog if it called `preventDefault()`, and sets `closeOnClick={false}` by default to mirror upstream's preventDefault; override it with `closeOnClick`. (3) PromptInputHoverCard still accepts `openDelay`/`closeDelay` (default 0) but they are applied to PromptInputHoverCardTrigger via context because Base UI PreviewCard puts delays on the trigger; passing `delay`/`closeDelay` directly on the trigger overrides them. (4) PromptInputSelect is Base UI Select: `onValueChange` receives `(value, eventDetails)` and the value may be `null`; PromptInputSelectValue renders the raw value unless you pass `items={[{ label, value }]}` on PromptInputSelect (or a children function). (5) `PromptInputButton`/`PromptInputSubmit` `onClick` receive Base UI's event type (a superset of React.MouseEvent). Behaviour fixed on top of upstream: (6) Enter submits only through an enabled `button[type=\"submit\"]` inside the form, so while PromptInputSubmit shows Stop (`status` submitted/streaming with `onStop`) Enter does nothing and the draft is kept; a disabled or missing submit button blocks Enter the same way. (7) `accept` understands `.ext` patterns (matched case-insensitively against the file name, so files the OS reports with an empty type still match), `type/*` and `*/*`; when only some files of a batch pass `accept` or `maxFileSize`, the rest are dropped and reported through `onError`, like `max_files`. (8) `onError` codes are `\"max_files\" | \"max_file_size\" | \"accept\" | \"screenshot\"`; the `PromptInputError` type is exported. (9) When `onSubmit` throws or rejects, an uncontrolled PromptInputTextarea gets its text back unless you typed since (attachments and referenced sources are kept, as upstream); text held by PromptInputProvider is never cleared on failure. (10) `syncHiddenInput` is accepted for parity, but browsers cannot set a file input's value: it only clears the hidden input when the attachment list empties, and native form posts never carry the attachments. (11) PromptInputTextarea has `aria-label=\"Message\"` by default; override it via props. (12) PromptInputButton tooltips open immediately and, because Base UI tooltips carry no ARIA, their text is mirrored into a visually hidden `aria-describedby` description unless it equals the button's `aria-label`. (13) PromptInputTools wraps and PromptInputSubmit never shrinks, so a long toolbar does not overlap the submit button at phone widths; clicking the empty surface of PromptInputHeader/PromptInputFooter focuses the textarea (not the model select)."
- prompt-input › description: unchanged.
- prompt-input › dependencies: unchanged (`ai@^7`, `lucide-react`, `nanoid@^6`).

## Requests for other owners

- `registry/ai/registry.json`: replace the prompt-input `docs` string with the one above.
- `components/ui/select.tsx` (vendored) / Base UI: with the select open, Base UI's modal Select renders floating-ui focus guards (`span[data-base-ui-focus-guard]` with `aria-hidden="true"` and `tabindex="0"`) that axe's `aria-hidden-focus` rule (serious, wcag2a) reports. Every test that scans a page with an open Base UI Select (or Dialog) will hit it. - `registry/blocks/chat` (chat fixer): the root cause of chat-block-and-leaves.md:F2 is fixed here (Enter is a no-op while the Stop button is rendered); the block-level guard in `ChatComposer.handleSubmit` is still worth keeping for programmatic submits.
