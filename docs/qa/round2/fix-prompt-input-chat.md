## Fixed

- prompt-input-chat:F1 / rendered-surface:N2 (high) — `ChatComposer.handleSubmit` no longer returns the consumer's promise (`void onSubmit(message)`), and both shipped pages call `void sendMessage(...)` instead of returning it; in prompt-input the post-submit commit snapshots the ids of the files and referenced sources the submit carried and removes only those (`removeAttachments`/`removeReferencedSources`), so a file attached while an async `onSubmit` is pending survives — `registry/blocks/chat/components/blocks/chat.tsx:697-701`, `registry/blocks/chat/page.tsx:24`, `app/preview/chat/page.tsx:43`, `registry/ai/prompt-input.tsx:732-757, 905-915` — tests: `tests/browser/blocks/chat.test.tsx` › "clears sent files from the composer once the message is sent, not when the answer ends" (failed before: `expected 1 to be +0`; passes after), › "keeps a file attached while the previous answer streams" (failed before: `Cannot find element with locator: getByRole('button', { name: 'Remove later.txt' })`; passes after); `tests/browser/ai/prompt-input.test.tsx` › "clears only what the submit carried once a pending onSubmit resolves, with local state / a PromptInputProvider" (new; mutation m02 proves it fails on the old clear-everything commit). The `Demo` harness in the chat tests deliberately still returns `sendMessage`'s promise, so the block-level fix is what the two chat tests exercise.
- prompt-input-chat:F3 (medium) — `PromptInput.onSubmit` may now return `false` (sync or from its promise) to reject the submit: the text is restored (existing machinery) and attachments and sources are kept; the type is `void | boolean | Promise<void | boolean>`. `ChatComposer.handleSubmit` returns `false` while generating (the Enter and click guards stay) — `registry/ai/prompt-input.tsx:535-543, 953-958`, `chat.tsx:694-697` — tests: `chat.test.tsx` › "keeps the draft and the attachments when a programmatic form submit is rejected while generating" (failed before: `expected '' to be 'queued'`; passes after, and it then submits the kept draft and file once ready); `prompt-input.test.tsx` › "keeps the draft, attachments and sources when a sync / an async onSubmit returns false" (new; mutation m01).

## Registry entry changes (exact strings; the registry owner applies them)

- prompt-input › description: "Chat composer for AI apps: an auto-growing textarea that submits on Enter (Shift+Enter for newlines), a footer/header tools row, an attachment action menu (add files, take screenshot), model select, hover-card and command-palette slots, and a submit button that turns into a stop button while submitted or streaming when onStop is provided. Handles file attachments via drag-drop, paste, and file dialog with accept/maxFiles/maxFileSize validation, converts blob URLs to data URLs on submit, and can lift its state into an optional PromptInputProvider. Use it as the input at the bottom of any AI SDK useChat conversation. Composes input-group, dropdown-menu, select, tooltip, hover-card, command, spinner."
- prompt-input › docs: "Built for the Base UI styles (base-nova): it composes the Base UI wrappers from components/ui and relies on their render prop and event signatures, so it does not work on Radix or React Aria styles. Ported from Radix to Base UI. API changes vs AI Elements: (1) PromptInputActionAddScreenshot takes `onClick` instead of Radix `onSelect`; calling `event.preventDefault()` in it skips the capture, but the menu still closes (pass `closeOnClick={false}` to keep it open). Capture failures other than a denied or cancelled picker go to PromptInput's `onError` as `{ code: \"screenshot\", message }`, or to `console.error` when there is no handler. (2) PromptInputActionAddAttachments and PromptInputActionMenuItem are Base UI Menu items: use `onClick` (not `onSelect`) and `closeOnClick={false}` to keep the menu open. PromptInputActionAddAttachments calls your `onClick` first, skips the file dialog if it called `preventDefault()`, and sets `closeOnClick={false}` by default to mirror upstream's preventDefault; override it with `closeOnClick`. (3) PromptInputHoverCard still accepts `openDelay`/`closeDelay` (default 0) but they are applied to PromptInputHoverCardTrigger via context because Base UI PreviewCard puts delays on the trigger; passing `delay`/`closeDelay` directly on the trigger overrides them. (4) PromptInputSelect is Base UI Select: `onValueChange` receives `(value, eventDetails)` and the value may be `null`; PromptInputSelectValue renders the raw value unless you pass `items={[{ label, value }]}` on PromptInputSelect (or a children function). (5) `PromptInputButton`/`PromptInputSubmit` `onClick` receive Base UI's event type (a superset of React.MouseEvent). Behaviour fixed on top of upstream: (6) Enter submits only through an enabled `button[type=\"submit\"]` inside the form, so while PromptInputSubmit shows Stop (`status` submitted/streaming with `onStop`) Enter does nothing and the draft is kept; a disabled or missing submit button blocks Enter the same way. (7) `accept` understands `.ext` patterns (matched case-insensitively against the file name, so files the OS reports with an empty type still match), `type/*` and `*/*`; when only some files of a batch pass `accept` or `maxFileSize`, the rest are dropped and reported through `onError`, like `max_files`; in provider mode `maxFiles` is enforced across several `add()` calls in one handler, not only per call. (8) `onError` codes are `\"max_files\" | \"max_file_size\" | \"accept\" | \"screenshot\"`; the `PromptInputError` type is exported. (9) `onSubmit` may return `false` (directly or from its promise) to reject a submit. When it throws, rejects or returns `false`, an uncontrolled PromptInputTextarea gets its text back unless you typed since, and attachments and referenced sources are kept (as upstream); a textarea you control through `value` is left to you, and text held by PromptInputProvider is never cleared on failure. Once a submit is accepted, only the attachments and referenced sources it carried are cleared, so a file attached while an async `onSubmit` is still pending stays; a chat page should still not return `sendMessage`'s promise from `onSubmit` (see @uifiles/chat). (10) `syncHiddenInput` is accepted for parity, but browsers cannot set a file input's value: it only clears the hidden input when the attachment list empties, and native form posts never carry the attachments. (11) PromptInputTextarea has `aria-label=\"Message\"` by default; override it via props, or pass `aria-label={undefined}` to defer to a visible `<label htmlFor>` or `aria-labelledby`, since `aria-label` outranks a native label. (12) PromptInputButton tooltips open immediately and, because Base UI tooltips carry no ARIA, their text is mirrored into a visually hidden `aria-describedby` description unless it equals the button's `aria-label` or its visible text; an empty tooltip (`\"\"` or `{ content: \"\" }`) renders no tooltip and no description. (13) PromptInputTools wraps and PromptInputSubmit never shrinks, so a long toolbar does not overlap the submit button at phone widths; clicking the empty surface of PromptInputHeader/PromptInputFooter focuses the textarea (not the model select), while clicks on anything that takes focus or handles clicks itself (buttons, links, form controls, `tabindex` elements, `contenteditable`, labels and ARIA widget roles) leave focus where they put it."
