## Findings (most severe first)

### R3-1. The `d` theme hotkey is a character-key shortcut with no way to turn it off or remap it — severity: high (WCAG 2.1.4, Level A; docs site only)
- Where: `components/theme-provider.tsx:58-90` (`ThemeHotkey`: a `window` keydown listener toggling the theme on a bare `d`/`D`, active whenever the target is not in `HOTKEY_EXCLUDED_SELECTOR`); `components/theme-toggle.tsx:38,46` (`aria-keyshortcuts="D"`, `<kbd>D</kbd>`); rendered on every page including previews and the 404.
- What: WCAG 2.1.4 Character Key Shortcuts (Level A) requires a single-character shortcut to be switchable off, remappable, or active only while the relevant component has focus. Here it is none of those: `d` flips the theme with focus on `<body>`, on any plain button, on any link, on the collapsible triggers and inside the pinned citation card (R3-7). Neither round 1 nor round 2 assessed 2.1.4 (`grep "2.1.4|Character Key"` over all round-1/2 reports: nothing); they only checked the exclusions (F22), which are correct as far as they go.
- Evidence: `probe-r3.log` hotkey-2.1.4: `onBody false → afterBody true → afterButton false → afterLink true`; no settings control, only `localStorage.theme`; `theme.log` "'d' and 'D' on body toggle the theme" (PASS by round-2 standards); `verify.log` N3 step 10: focus on the card's Next button, `d` → `toggled: true`.
- Why it matters: speech-input and some motor-impaired users trigger single-key shortcuts accidentally (the criterion's rationale); the site advertises a WCAG 2.2 AA gate, and this is Level A. It ships only on the docs site, not in any registry item.
- Proposed fix: require a modifier (`Alt+D` or `Ctrl/⌘+Shift+D`; update `aria-keyshortcuts` and the `<kbd>` hint), or drop the hotkey and keep the button. A unit test on `ThemeHotkey` that a bare `d` does nothing and the combo toggles.

### R3-2. Inline-citation: paging to a carousel end with the keyboard drops focus to `<body>`, and Escape can then not return it to the badge (N3 residual) — severity: high (shipped component; keyboard focus loss)
- Where: `registry/ai/inline-citation.tsx:511` and `:540` (`disabled={!canScrollPrev}` / `disabled={!canScrollNext}` on the Prev/Next buttons) combined with `:161-163` (`restoreFocusRef` is set only when `popupRef.current.contains(document.activeElement)` at Escape time).
- What: pin the card (Enter), Tab to Next, Enter → the index reads `2/2` but the button that had focus becomes `disabled`, so Chromium moves focus to `<body>`. The card stays open (pinned), the user's focus is at the top of the document, and pressing Escape closes the card with focus left on `<body>`; the "Escape returns focus to the badge" behaviour only works before the first page turn. With two sources (the preview, and the common case) *every* keyboard page turn does this. The same happens for Prev at `2/2 → 1/2`.
- Evidence: `probe-r3.log` citation-focus: "Enter on Next → 2/2 … `active: { tag: "BODY" }`" (Next `disabled: true`, no `aria-disabled`); "Escape after paging … `cards 0, active BODY`"; "Enter on Prev at 2/2 → 1/2 … `active BODY`". `verify.log` N3 steps 4–6 show the cascade (the follow-up Enter on `<body>` does nothing). `shots/r3-citation-after-next.png` (2/2, no focus ring anywhere), `shots/n3-citation-page2-keyboard.png`.
- Why it matters: this is the keyboard path round 2 asked for and the fix report describes as "the card's controls are reachable"; reaching them and then losing focus at the first end is a WCAG 2.4.3 focus-order failure in a registry item consumers install.
- Proposed fix: keep the buttons focusable at the bounds (`aria-disabled` + no-op click, the usual carousel pattern), or before disabling move focus to the other arrow / the popup (`popupRef.current.focus()`); also let the Escape restore path use "focus is inside the popup *or* the card is pinned" instead of only "inside". Extend `tests/browser/ai/inline-citation.test.tsx` › "moves focus into the card on Enter…" to press Enter on Next at the last page and assert `document.activeElement` is still inside the popup, then Escape → badge.
- Test written: none (lens rule). Repro: `node probe-r3.mjs`.

### R3-3. `branch`: the selector is still absent from the production server HTML although `fix-leaves-tokens` reports F5 fixed and `tests/unit/ssr.test.ts` asserts it — severity: low (behaviour as in round 2), plus a test-quality issue
- Where: `registry/ai/branch.tsx:66-78` (`countBranches` matches `child.type === MessageBranchContent`), `:207-210` (`MessageBranchSelector` returns `null` for `totalBranches <= 1`); `app/preview/branch/page.tsx` (server component composing the client components).
- What: the served `/preview/branch` (byte-identical to `.next/server/app/preview/branch.html`) contains the three branch wrappers (`… block` / `… hidden` / `… hidden`) but no `ButtonGroup`, no `aria-label="Previous branch"/"Next branch"` and no "1 of 3": the only `aria-label`s in the document are Copy Code, Download file, Previews, Toggle theme. The render-time count works under `renderToString` in one Vitest bundle (the unit test) but not through Next's RSC → SSR pipeline, where the elements a server component passes as `children` do not compare equal to the client module's `MessageBranchContent`; the count falls back to the layout-effect registration and the selector appears after hydration, exactly the round-2 F5 shape (no hydration warning: `hydration.log` 0/0/0 over 3 loads × 3 widths; `branch.log` Prev/Next enabled after hydration, wraps 1→2→3→1→3).
- Evidence: `served-branch.html`; the node extraction in the commands log: `prevNext: 0, hiddenWrappers: 2, blockWrappers: 1, buttonGroup: 0`; `branch.log` `ssrButtons: []` (same as round 2); `fix-leaves-tokens.md` › Fixed › F5 and the `branch` docs string ("…so the selector and MessageBranchPage ("2 of 3") are in server-rendered HTML").
- Why it matters: the shipped `docs` string and the unit test promise something the real page does not do; without JS the reader gets the first branch and no controls (as before). Low, but the false confidence should not survive into the PR.
- Proposed fix: either assert it where it is real — an e2e check that `page.request.get("/preview/branch")` contains `aria-label="Next branch"` (it will fail today) — and fix the count (compare by a `$$typeof`-independent marker such as a static property on `MessageBranchContent`, or an explicit `count` prop), or drop the claim from `docs` and the unit test.

## Verdict

**Not yet.** The rendered surface has converged hard: zero console output and zero axe violations on every page in every context, no overflow to 320 px, every tab stop ringed at both widths, the round-2 highs and mediums (N1, N2) fixed and proven by mutation, the model-selector preview hermetic, the chat block clean on desktop, phone and touch. Two things block, both one-line fixes:

1. **R3-1** (high): the bare `d` theme hotkey fails WCAG 2.1.4 (Level A) — require a modifier or remove it (`components/theme-provider.tsx`, `components/theme-toggle.tsx`).
2. **R3-2** (high): in the shipped `inline-citation`, paging to a carousel end from the keyboard drops focus to `<body>` and Escape then cannot return it to the badge — `aria-disabled` (or move focus) instead of native `disabled` on the arrows, plus the Escape restore path for a pinned card (`registry/ai/inline-citation.tsx:511,540,161`).

Follow-up, not blocking: R3-3 (branch selector is not in the production SSR HTML although the fix report, the `docs` string and `ssr.test.ts` say it is), R3-4 (five client previews and the 404 still titled "uifiles"), R3-5 (queue clamp/truncate under text spacing, no `title`), R3-6/R3-7 (nits), N8 (build-time warning only) and F17 (owner decision).
